## Lessons from the spec phase (written to memory)

- **Big decisions need spec first, code second**: 5 spec docs (60KB) froze "why", no rework in 12 weeks of code
- **Trunk-based + short commit messages**: all 8 commits small (< 500 lines), review-friendly
- **Decisions in matrix form**: decision-log §5.1's 8-crate × visibility matrix is easier to look up than scattered prose
- **"Hard lines" list separating from reference (dsh)**: arch-map §10's 8 red lines, directly checkable in later code review

## Collaboration mode with user (confirmed today)

- **Commit frequency**: one commit per decision point, subject line ≤ 72 chars, body explains why
- **Review rhythm**: I write a section, user glances, give feedback if any, continue if not
- **Decision mechanism**: big decisions user decides ("your call" / pick recommendation / give specific value), small decisions I just go
- **Progress report**: hourly, gate-discipline silent (no progress no interruption)
- **No redo**: once a decision is archived, changing it requires a new commit + spec update, not editing old docs
